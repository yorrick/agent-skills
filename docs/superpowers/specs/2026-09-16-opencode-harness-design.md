# opencode harness for agent-skills

**Date:** 2026-09-16
**Status:** design approved, not yet implemented
**Branch:** `feat/opencode-harness` (cut from `origin/main`)
**Repo:** https://github.com/yorrick/agent-skills

## Goal

Make this repository installable in opencode the same way it is installable in
Claude Code and Codex: write the skill once, install it from GitHub with no
symlinks and no per-skill configuration. This adds opencode as the third
supported harness.

## Decisions from brainstorming

1. **One repo-level entry.** opencode has no marketplace concept: a plugin is a
   git spec in `opencode.json`, and a git spec installs the whole repository as
   one package. The repo therefore exposes a single plugin entry that registers
   everything. The per-plugin versions in the generated marketplace files are
   not reflected in opencode, and that is accepted. The repo tag or commit of
   the git spec is the version.
2. **Scope: skills plus commands.** All eight plugins become usable: seven via
   their `skills/` directories, `dev-loop` via its three `commands/*.md` files.
   The `self-improve-skill` SessionStart/SessionEnd hooks are explicitly
   deferred (non-goal for this change).
3. **Third supported harness, not personal convenience.** The deliverable
   includes README/AGENTS/CLAUDE documentation, generated marketplace wording,
   and a CI check, so the entry cannot rot silently.
4. **Approach A: dynamic entry.** The entry file discovers plugins at load time
   instead of hardcoding them. The manifest generator gains exactly one new
   target: the root `package.json`. No generated JavaScript.
5. **Command registration is additive.** Registered command names are the
   filenames (`dev-loop`, `review-loop`, `workflow`), and an existing command
   with the same name in the user's config is left untouched, so user-defined
   commands always win.

## Architecture

Five new files and five modified files, with no change to how Claude Code and
Codex consume the repository.

New:

- `package.json` (repo root, generated by `scripts/sync_manifests.py`)
- `.opencode/plugins/agent-skills.js` (hand-written entry, the only new logic)
- `.opencode/INSTALL.md` (install and update instructions for opencode users)
- `tests/test_opencode_entry.py` (CI, assertions)
- `tests/opencode_entry_harness.mjs` (CI, node fixture)

Modified:

- `scripts/sync_manifests.py`: one more generated target and the marketplace
  description wording
- `supabase-security/skills/supabase-security/SKILL.md`: portable plugin-root
  resolution (see Components)
- `README.md`, `AGENTS.md`, `CLAUDE.md`: opencode documented as a third harness
  (see Documentation)

### Load path

1. User adds one line to `opencode.json`:
   `"plugin": ["yorrick-agent-skills@git+https://github.com/yorrick/agent-skills.git"]`
2. opencode (bun) installs the git repository into `~/.cache/opencode/packages`.
3. opencode resolves `package.json` `main` to `.opencode/plugins/agent-skills.js`
   and imports it. The module must export only functions (the legacy loader
   throws on non-function exports).
4. opencode calls the exported plugin function and later calls its `config` hook
   with the resolved config singleton.
5. The `config` hook mutates that singleton: it pushes each plugin's `skills/`
   directory onto `config.skills.paths` and registers each `commands/*.md` file
   into `config.command`.
6. opencode discovers skills lazily from `config.skills.paths` (so they appear
   in the system prompt's skill list) and builds the command menu from
   `config.command`.

No bootstrap injection is needed: opencode already lists available skills in its
system prompt, so the message-transform trick other projects use has no
equivalent job here.

### Discovery invariant

The entry treats a top-level directory as a plugin if and only if it contains
`plugin.toml`, the same invariant `scripts/sync_manifests.py` enforces
(`load_plugins()`). The directory name is the plugin name, guaranteed by the
generator's name check. This automatically excludes `docs/`, `scripts/`,
`tests/`, `.worktrees/`, and local-only directories such as
`investigate-incident/` which has no `plugin.toml`.

State on the target branch: 8 plugins; 7 have `skills/`; `dev-loop` is the only
commands-only plugin, with three commands.

## Components

### 1. Generated root `package.json`

Generated, never hand-edited, so it cannot drift. `sync_manifests.py` writes:

- `name`: `yorrick-agent-skills` (must match the name used in the documented
  plugin spec)
- `version`: the maximum of the plugin versions from `plugin.toml` files, parsed
  as `x.y.z` tuples with no new dependency. The field exists to satisfy the
  package format; it never drives updates (opencode keys its cache on the git
  spec and lockfile).
- `type`: `module` (the entry uses ESM imports)
- `main`: `.opencode/plugins/agent-skills.js`
- `description`: the existing `MARKETPLACE_DESCRIPTION` constant
- `license`: `MIT`

The existing CI step `uv run scripts/sync_manifests.py --check` covers it
automatically once it is a target.

### 2. The entry: `.opencode/plugins/agent-skills.js`

Node builtins only (`fs`, `path`, `url`), no dependencies, so CI needs no
`npm install` and the installed package has no transitive deps.

Behavior, in the `config` hook:

1. Locate the repo root from `import.meta.url` (`__dirname/../..`).
2. Read the top-level directory entries, keep those containing `plugin.toml`.
3. For each, push `<dir>/skills` onto `config.skills.paths` if it exists.
   Idempotent: never add a path twice.
4. For each, register every `<dir>/commands/*.md` if the directory exists:
   - Parse YAML frontmatter with a minimal parser (key: value lines).
   - Map `description` to `config.command[name].description`.
   - Strip frontmatter; the remaining body is the `template`.
   - Substitute every `${CLAUDE_PLUGIN_ROOT}` with the owning plugin's absolute
     directory. opencode sets no plugin-root variable, and one variable could
     not serve eight plugins anyway.
   - Leave `$ARGUMENTS` in place: it is opencode's own placeholder, and the
     command files already use it.
   - Skip registration if `config.command[name]` already exists (user commands
     win).
5. Initialize `config.command` and `config.skills` defensively.

Only `allowed-tools` and `argument-hint` frontmatter fields are ignored; the
command files themselves stay untouched so Claude Code and Codex keep their
existing behavior.

The export is a single async function returning `{ config }`.

### 3. Shared skill fix: portable plugin root

`supabase-security/skills/supabase-security/SKILL.md:263` currently reads
`${CLAUDE_PLUGIN_ROOT:-}/scripts/audit_rls.py`, which resolves nowhere in
opencode. Adopt the self-locating idiom that
`pr-review/skills/pr-review/SKILL.md:29` already uses: try the environment
variable, otherwise derive the plugin root from the skill's own location. The
skill file stays verbatim across harnesses, and Codex benefits from the same
fix.

### 4. Documentation

- `README.md`: add opencode to the supported harnesses and show the one-line
  install snippet plus the restart note.
- `AGENTS.md` / `CLAUDE.md`: add opencode to the harness descriptions.
- `.opencode/INSTALL.md`: install, verify, update (cache caveat: a restart alone
  may not fetch a newer commit; clearing the opencode package cache does), and
  the note that git tags do not exist yet so installs track `main`.
- `scripts/sync_manifests.py`: `MARKETPLACE_DESCRIPTION` grows from "(Claude
  Code and Codex)" to include opencode; one edit regenerates both marketplace
  files.

### 5. CI test: `tests/test_opencode_entry.py`

A pytest that shells out to `node` (present on GitHub's ubuntu runners) running
`tests/opencode_entry_harness.mjs`. The harness imports the entry, calls the
plugin function with a stub input, calls the `config` hook against an empty
object (and again against a seeded one), and prints the resulting config as
JSON. pytest then asserts, deriving expectations from the filesystem rather
than hardcoding counts:

- every directory with `plugin.toml` and a `skills/` subdirectory appears in
  `config.skills.paths`; directories without one do not
- each registered skills path contains at least one `*/SKILL.md`
- the registered command names are exactly the `*/commands/*.md` basenames
- no command template contains `${CLAUDE_PLUGIN_ROOT}` or leading frontmatter
- calling the hook twice adds nothing twice
- a pre-seeded `config.command.workflow` is left byte-identical
- the module exports only functions

The test file must satisfy the existing CI gates: `ruff format --check`,
`ruff check scripts/ tests/`, and `pyright`.

## Edge cases handled

- Plugin with no `skills/` (dev-loop) or no `commands/` (the other seven).
- Plugin with both: both get registered.
- Command file without frontmatter: whole file is the template, no description.
- `config.command` or `config.skills` undefined on first load.
- Duplicate registration across repeated hook calls.
- Local-only plugin directories without `plugin.toml` are ignored by design.

## Non-goals

- Porting `self-improve-skill`'s hooks to opencode events.
- Introducing git tags or pinning the opencode install to a version.
- Any change to Claude Code or Codex installs.
- Namespacing command names (for example `dev-loop:workflow`); plain filenames
  with skip-if-exists were chosen, and colon support is unverified.

## Testing and verification

Automated (CI):

- the new pytest described above, inside the existing `uv run pytest tests/` step
- `uv run scripts/sync_manifests.py --check` proves `package.json` is current
- existing gates unchanged

Manual end to end, before claiming done:

1. Check whether opencode honors `#branch` in a git plugin spec (docs only
   promise `#tag`). If yes, install this branch directly. If no, merge first
   and install from `main`.
2. `opencode run "list your skills"` shows the seven portable skills
   (agent-session-monitor, flowchart, pr-review, reflect, supabase-security,
   task-status, visual-design-review) alongside the pre-existing ones.
3. The three dev-loop commands appear in the command menu and one of them
   resolves `${CLAUDE_PLUGIN_ROOT}` to the real path (inspect the template via
   the harness output, since running a full dev-loop is out of scope).
4. `claude plugin marketplace update yorrick` still works and Claude Code still
   sees its plugins after the shared skill edit.
